## 一、两条更正（我之前说错了）

1. **9 月那两次不是「非正常关机/供电尖峰」，是蓝屏。**
   解析 `C:\Windows\Minidump\*.dmp` 的 DUMP_HEADER64（BugCheckCode @ 0x38）：

   | 转储 | 时间 | BugCheck |
   |---|---|---|
   | `082726-8296-01.dmp` | 2026-08-27 13:46 | **0x9F DRIVER_POWER_STATE_FAILURE** |
   | `092426-9062-01.dmp` | 2026-09-24 06:41 | **0x9F**（param1 = 3） |
   | `092626-11000-01.dmp` | 2026-09-26 18:36 | **0x9F**（param1 = 3） |

   `MEMORY.DMP` 3.57 GB（09-26）。`0x9F` = **某设备对象阻塞电源 IRP 过久**
   → 电源状态转换（睡眠/唤醒/关机）失败，不是断电。

2. **WHEA 事件与 C 盘损坏无关。撤回。**
   解码 WHEA-Logger ID=3 的 `RawData`：签名 `CPER`、`ErrorSeverity=3 = Informational`、
   内容只有一条厂商设备路径 `VenHw(93A41C2F-…)`，且 **6 次出现全在开机后 ~15 秒内**。
   ⇒ 是固件在开机时写的**信息级**记录，不足以断定硬件故障。

## 二、C 盘损坏 = 那次 Linux 会话被强制断电（证据链闭合）

```
10-07 23:20:51  Ntfs: 卷 C: 【需要进行在线扫描】    ← 脏位已置上
10-07 23:20:52  Ntfs: 卷 D: 运行状况良好（另 4 卷同）
```

- 10-01 之后 Windows 侧 **没有任何 41 / 6008 / 1001**（无蓝屏、无非正常关机）
- **只有 C: 脏，D: 与另外 4 个卷全部干净**
- ⇒ 那 86 分钟里跑的是 Linux，**C: 以 RW 挂载被写入，未 `sync; umount` 就被强制断电**
- ⇒ **与「Linux 跑着跑着黑屏、只能强制关机」在时间与机制上完全吻合 —— 极可能是同一件事**

**所以「黑屏」与「C 盘损坏」是同一个根因的两个后果，不是两件独立的事。**

## 三、显卡：有驱动栈线索，但不能说显卡硬件坏了

| 项 | 事实 | 判读 |
|---|---|---|
| 三次蓝屏 | 全是 `0x9F`（设备阻塞电源 IRP） | 指向**驱动电源状态处理**，显示驱动是高发区 |
| **第三块显示适配器** | **`MuMu Virtual Display Adapter`（`ROOT\DISPLAY\0000`，oem75.inf）**，且 `MuMuRemoteService` 为 **Auto + Running** | 第三方虚拟显示适配器 + 常驻自启 ⇒ `0x9F` 的**合理嫌疑**，值得排除 |
| `nvlddmkm` 错误 153 | 2 条：09-26 22:40、09-28 11:17 | ⚠ **近 3 天 0 条**，Windows 侧 GPU 驱动近期没报错 |
| Display TDR (4101) | **0 条** | 没有驱动超时恢复记录 |
| 驱动版本 | Intel `32.0.101.7092`(09-03)、NVIDIA `32.0.16.1088`(07-22) | 都不旧 |
| `Kernel-PnP 219 ×60` | 每次开机 4 个设备 WUDFRd 加载失败，**但设备最终 Status=OK** | **良性开机时序噪声**（同 `DriverFrameworks 10118`），**别当故障** |
| `Kernel-Processor-Power 37 ×80` | 「处理器速度受系统固件限制」 | CPU 被固件/EC 限速（功耗/温度墙）。非崩溃原因，但说明平台在限功耗 |

**结论**：Windows 侧的问题是「**驱动栈**」（尤其是那个虚拟显示适配器），
**没有证据说是 3080Ti 或 Intel 核显的硬件坏**。
Linux 黑屏本身**拿不到任何证据**——近 3 天 Windows 日志里没有任何崩溃记录，
说明黑屏是 Linux 侧事件，必须在 Linux 侧取证。

## 四、Linux 侧取证（唯一能把黑屏钉死的路径）

**黑屏当下（如果机器还活着）：**
```bash
# 1) 先测这两个——它们直接区分「显示栈挂了」还是「内核/硬件死了」
#    a. 按 CapsLock：灯还亮/灭切换吗？
#    b. 另一台机器 SSH 进来：
ssh rosary@<ip>  'dmesg | tail -80'
```

**强制重启后立刻做：**
```bash
# 上一次启动的内核日志（前提：journal 已持久化）
ls /var/log/journal            # 不存在就先开：sudo mkdir -p /var/log/journal && sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo journalctl -k -b -1 -p warning --no-pager | tail -100
sudo journalctl -k -b -1 --no-pager | grep -iE 'i915|nvidia|drm|gpu|nvme|thermal|mce|hardware error'

# 内核 oops/panic 会跨越重启留在 pstore（如果固件支持）
sudo ls -l /sys/fs/pstore/
sudo cat /sys/fs/pstore/dmesg-* 2>/dev/null | tail -100
```

**如果 pstore 为空且 journal 没落盘**，那黑屏就必然无痕。这种情况下的替代：
- 开持久 journal（上面的 `mkdir /var/log/journal`）
- 或加内核参数 `pstore.backend=efi` / 确认 BIOS 里 pstore 可用
- 或在 Grub 里给内核加 `console=tty0 loglevel=7` 并接外接显示器，看黑屏时屏幕是否还有内核输出

**三个已知高发成因（按可能性排，仅供缩小范围，不是从你的日志推出的结论）：**
1. **i915 显示栈挂死**（随机黑屏的经典成因）——经验性缓解：内核参数 `i915.enable_psr=0`、
   `i915.enable_dc=0`。**属经验手段，不是诊断结论**；改之前先拿到上一步的日志。
2. **内存/IO 雪崩**——我们前几轮确实让 Linux 侧 OOM 过一次（8G 峰值 + GPU 纹理 churn），
   那次你也说「刚刚直接重启系统了」。**这条不能排除，优先级不低。**
3. **NVMe APST 电源管理挂死**（三星 MZVL22T0HBLB）——验证：内核参数
   `nvme_core.default_ps_max_latency_us=0`。

## 五、C:/D: 风险处置（建议已按「只读不成立」重算）

**分区事实**（`Get-Partition -DiskNumber 0`，GPT，Samsung 1908 GB NVMe）：

| # | 盘符 | 大小 | GPT 类型 GUID | 含义 |
|---|---|---|---|---|
| 1 | C: | 500 GB | `ebd0a0a2-…99c7` | Windows |
| 2–5 | — | 0.88–1.12 GB | `de94bba4-…6ac` | Recovery |
| 6 | — | 0.29 GB | `c12a7328-…c93b` | EFI |
| 7 | D: | 1000 GB | `ebd0a0a2-…99c7` | Windows |
| **8** | — | **149.94 GB** | `0fc63daf-…7de4` | **Linux filesystem** |
| **9** | — | **253.61 GB** | `0fc63daf-…7de4` | **Linux filesystem** |

### ✅ 正解：把 Linux 侧的工作副本放到 #8 / #9（403 GB 原生空间）

这正面回应「只读肯定不行」——**不是让你只读，是让你写到你自己的原生分区**，
`git clone` 到那边，写操作根本不碰 NTFS。

### ❌ 不建议「搬到 D:」

- 风险的载体是「**Linux RW 写某个 NTFS 卷**」。仓库搬到 D: 只是把这个动作搬过去，风险跟随转移。
- **D: 上还住着应用的数据目录**（`AppData\Roaming\com.rosary.andengyuanhui` 是指向
  `D:\安得云荟\data` 的**符号链接**）⇒ 仓库与 app 数据放同一卷 = **合并两个失败域**。
- 10-07 那次只有 C: 脏、D: 干净 ⇒ **正因为那次 Linux 只写了仓库所在的 C:。**

### 若必须在 NTFS 上跨系统交换

- **NTFS 只当「传输介质」**：放 `git bundle` / 压缩包这类**单个大文件**；
  不要把「数万小文件 + 构建」的工作目录放在上面（那正是这次踩雷的负载形态）。
- 同步流程：Linux 侧开发在原生分区 → `git bundle` 或 push 到远端 → Windows 侧 `git pull`。

### 无论挂哪块 NTFS 都要有的纪律

```bash
sync; sudo umount /mnt/win_c      # 退出 Linux 前必须做
```
**绝不在 NTFS 处于挂载状态时强制关机**（这次 C 盘损坏的直接原因就是它）。
从 Linux 回 Windows 后，`chkdsk C: /scan`（只读、安全）。
