# 规划与任务拆解（Planning & Task Breakdown）

## 概述

把大任务拆成"可独立交付、可独立验证"的薄片。每片应在一次提交内完成并验证，降低中途偏航与返工成本。

## 何时使用

- 需求涉及多个文件或多阶段
- "怎么做"尚不明确，需要先定结构再动手
- 重构、迁移、跨模块联动修改
- 估计工作量超出一两小时

**何时不用**：单文件小改、明显的一行修复、探索性原型。

## 拆解流程

### 1. 理解目标边界
- 用一句话说清"完成时什么样"（验收标准）。
- 明确**不做什么**（范围边界），避免范围蔓延。
- 列出约束：性能、兼容性、依赖许可、不能动的模块。

### 2. 识别风险与未知
- 哪些部分你不理解？先读代码/查文档消除未知，再拆解。
- 哪些部分高风险（并发、安全、外部依赖）？优先拆得更细、先做验证性原型。
- 不要把"我不知道怎么做"藏进一个大任务里——单独列为调研子任务。

### 3. 拆成垂直薄片
- 垂直薄片 = 端到端可验证的最小行为单元（能跑、能测、能演示），而非水平层（先做所有数据层再做所有 UI）。
- 每片应有明确的"完成定义"：跑通什么测试 / 演示什么行为。
- 片与片之间尽量解耦：后一片不依赖前一片的内部实现，只依赖其行为契约。

### 4. 排序与依赖
- 先做风险最高或未知最多的片（降低后期返工）。
- 先做被其他片依赖的契约/接口。
- 把"锦上添花"的片排到最后，即使没做完也可交付。

### 5. 边做边修正
- 每完成一片后回顾：剩余拆解还合理吗？发现新未知就重新拆。
- 计划是工具不是契约——发现更好的结构就调整，但记录为何调整。

## 好薄片 vs 坏薄片

| 好薄片 | 坏薄片 |
|---|---|
| 端到端可验证（能跑测试） | 只完成一层（所有 model，再所有 view） |
| 一次提交可完成 | 跨多日多提交纠缠 |
| 有明确完成定义 | "把这块做好" |
| 独立可回滚 | 与其他片强耦合 |
| 风险前置 | 把难的部分堆到最后 |

## 验证

- [ ] 每片有明确的验收标准（跑通什么）
- [ ] 范围边界（不做什么）已写明
- [ ] 风险/未知已识别并前置
- [ ] 片间依赖清晰、最小化
- [ ] 计划可被中途调整且记录变更原因
