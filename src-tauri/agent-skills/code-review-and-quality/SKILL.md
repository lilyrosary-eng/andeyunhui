# 代码审查与质量（Code Review & Quality）

## 概述

沿五个轴系统地审查改动，避免"看起来没毛病"式的浅审查。每轴独立评估，发现问题按严重度分级反馈。

## 何时使用

- 提交前自审
- 审查他人 PR
- 合并前质量把关
- 接手陌生代码前评估其健康度

## 五轴审查

### 轴 1：正确性
- 改动是否做了它声称做的事？
- 边界情况覆盖了吗（空值、零、负数、超大输入、并发）？
- 错误路径是否被处理而非被吞？
- 是否有"看起来对但实际有 off-by-one/资源泄漏/竞态"的隐患？
- 测试是否覆盖了关键路径与边界？

### 轴 2：可读性
- 命名是否准确反映意图（看名字能猜对行为）？
- 是否有需要停顿解析的密集表达式？
- 注释解释"为什么"（有价值）还是"做什么"（噪音）？
- 与邻近代码风格一致吗？

### 轴 3：可维护性
- 改动是否让未来更难改（耦合、隐式约定、魔法数）？
- 抽象层次恰当吗（不过度也不不足）？
- 是否引入了"以防万一"的 speculative 抽象？
- 复杂度是否可被简化而不改行为？

### 轴 4：安全性
- 输入是否被信任（路径、命令、SQL、用户输入）？
- 是否有注入/路径穿越/SSRF/敏感信息泄漏风险？
- 权限与鉴权是否正确？
- 依赖是否来自可信源、许可是否合规？

### 轴 5：性能与资源
- 是否有不必要的 N+1 查询、重复计算、同步阻塞？
- 大数据结构是否在热路径上反复分配？
- 是否有资源未释放（文件句柄、连接、锁）？
- 是否过早优化或无依据地牺牲可读性换性能？

## 反馈分级

| 级别 | 含义 | 示例 |
|---|---|---|
| 🔴 阻断 | 必须改才能合并 | bug、安全漏洞、数据丢失风险 |
| 🟡 建议 | 强烈建议改 | 可读性差、边界未处理、缺测试 |
| 🟢 可选 | 改了更好，不改可接受 | 命名偏好、风格微调 |
| 💬 提问 | 不确定，请作者澄清 | "这里为什么用 X 而非 Y？" |

## 审查原则

- **对事不对人**：评代码不评作者。"这段可以简化"而非"你写复杂了"。
- **给依据**：反馈附理由或示例，而非纯偏好。
- **先理解再评**：不确定意图先问，别基于误判提反馈。
- **区分偏好与问题**：风格偏好标🟢，真正的问题标🟡以上。
- **表扬好的**：审查不只是找茬，看到巧妙实现也点出来。

## 验证

- [ ] 五轴逐一检查过（而非只看正确性）
- [ ] 反馈按严重度分级
- [ ] 每条反馈有依据或示例
- [ ] 区分了"问题"与"个人偏好"
- [ ] 阻断项有明确的修复方向
