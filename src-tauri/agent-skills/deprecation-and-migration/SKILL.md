# 弃用与迁移（Deprecation & Migration）

## 概述

代码是负债不是资产。Hyrum's Law 使移除困难。弃用规划在设计时就开始（"3 年后如何移除？"）。

## 何时使用

- 用新系统替换旧系统/API/库
- sunset 不再需要的功能
- 合并重复实现
- 删无人维护但被依赖的死代码
- 决定维护 legacy 还是投资迁移

## 弃用决策五问

1. 是否仍有独特价值？
2. 多少消费者依赖？
3. 替代是否存在？
4. 迁移成本？
5. 不弃用的持续维护成本？

## Advisory vs Compulsory

- **Advisory**（默认）：警告/文档/推动
- **Compulsory**：硬截止日 + 提供迁移工具/文档/支持

## 迁移四步

1. 先建生产可证替代
2. 公告 + 迁移指南
3. 增量迁移（一次一个消费者；Churn Rule：基础设施拥有者负责迁移用户）
4. 全部迁移后删旧（含测试/文档/配置/弃用通告）

## 迁移模式

- **Strangler**：流量比例渐进
- **Adapter**：旧接口包新实现
- **Feature Flag**：按用户切换

## 数据库 Schema（Expand/Contract）

- **EXPAND**：加可空新列
- **MIGRATE**：双写 + 批量回填
- **CONTRACT**：后续单独部署删旧列
- 每步可独立部署可回滚；每个迁移有测过的 down 路径
- 批量回填避免锁表；大索引用 CONCURRENTLY

## Zombie Code

- 无人维护但有活跃消费者，必须指派 owner 或带具体迁移计划弃用

## 红旗

- 弃用系统无替代
- 弃用公告无迁移工具/文档
- advisory 多年无进展
- zombie code 无 owner
- 向已弃用系统加新功能
- 未测当前用量即移除
- 删代码未验证零活跃消费者
- schema 变更与依赖代码同部署
- 原地 rename/drop 列
- 迁移无 down 路径或回填锁表

## 验证

- [ ] 替代已生产验证覆盖关键用例
- [ ] 迁移指南含具体步骤示例
- [ ] 所有活跃消费者已迁移（metrics/logs 验证）
- [ ] 旧代码/测试/文档/配置全删；无残留引用
- [ ] schema 迁移：附加阶段发布、每步新旧代码皆有效、有测过 down 路径、批量回填、破坏性步骤单独部署
