# 测试驱动开发（TDD）

## 概述

红-绿-重构：先写一条会失败的测试（红），写最小代码让它通过（绿），再在不改行为前提下改进结构（重构）。每一步都有测试兜底。

## 何时使用

- 新增功能或行为分支
- 修 bug（先写复现测试）
- 重构需要行为保障
- 设计尚不清晰、用测试驱动出接口

**何时不用**：探索性脚本/一次性代码；纯 UI 视觉调整（行为未定）；已有充分测试只需补实现。

## 红-绿-重构

### 红：先写失败测试
- 写一条测试，描述"想要的下一个行为"。一次只覆盖一个行为切片。
- 跑测试，确认它**因正确的原因失败**（断言失败，而非编译错误/环境问题）。
- 测试名描述行为："should reject expired token" 而非 "test token"。

### 绿：最小通过
- 写**最少**的代码让测试通过。不要加未要求的抽象、配置、扩展点。
- 允许写"丑"代码——重构阶段再清理。
- 跑测试，全绿。

### 重构：改结构不改行为
- 在测试全绿的保护下改进命名、提取函数、消除重复、调整结构。
- 每次小改后立即跑测试。红就 revert。
- 重构与功能改动分开提交。

## 原则

- **小步快走**：红→绿→重构的循环越短越好。一个循环加一个行为切片。
- **测行为不测实现**：测公共契约，不测私有方法/内部状态。否则重构时测试会碎。
- **隔离测试**：每条测试独立，不依赖执行顺序、不依赖共享可变状态。
- **AAA 结构**：Arrange（准备）→ Act（执行）→ Assert（断言）。三段清晰可读。
- **不为一行 getter/setter 写测试**：测有行为的方法；纯访问器由类型系统保障。

## 常见反模式

| 反模式 | 问题 |
|---|---|
| 一次写一堆测试再实现 | 循环过长，定位失败困难 |
| 测试依赖执行顺序 | 并行运行就崩；难以单独复现 |
| 断言内部状态而非输出 | 重构即碎，测试反而阻碍改动 |
| mock 一切 | 测的是 mock 不是真实行为 |
| 测试名是"test1/test2" | 失败时不知道丢了什么行为 |

## 验证

- [ ] 每条测试因正确原因失败过（红阶段确认）
- [ ] 测试描述行为而非实现
- [ ] 测试可独立运行、任意顺序通过
- [ ] 重构后测试仍全绿（未改行为）
- [ ] 覆盖了正常路径 + 边界 + 错误路径
