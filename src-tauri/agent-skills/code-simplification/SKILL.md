# 代码简化（Code Simplification）

## 概述

通过降低复杂度来简化代码，同时**严格保持行为不变**。目标不是更少的行数，而是让代码更容易读、理解、修改和调试。

每条简化都需通过一个简单测试："一个新团队成员能比看原版更快理解这段代码吗？"

## 何时使用

- 功能已工作且测试通过，但实现感觉比应有的更重
- 代码审查时被指出可读性或复杂度问题
- 遇到深层嵌套、超长函数或命名不清
- 合并引入了重复或不一致后

**何时不要用**：代码已干净；你还没理解代码做什么；性能关键且"更简"版本明显更慢；即将整体重写。

## 五原则

### 1. 严格保持行为
所有输入输出、副作用、错误行为、边界情况必须完全一致。不确定就不改。
- 输出对每个输入都相同吗？
- 错误行为一致吗？
- 副作用与顺序保持吗？
- 现有测试无需修改就通过吗？

### 2. 遵循项目约定
先读项目约定与邻近代码，匹配其风格（导入顺序、声明方式、命名、错误处理、类型标注深度）。破坏一致性的"简化"只是 churn。

### 3. 清晰优先于聪明
显式代码优于需要停顿解析的紧凑代码。能用具名中间变量说清意图，就不要用密集三元链。

### 4. 保持平衡
警惕过度简化：过度内联（删掉给了概念名字的 helper）、合并无关逻辑、移除"多余"但实为扩展性/可测性而存在的抽象、为行数优化。

### 5. 限定范围
默认只简化最近改动的代码。不要顺手重构无关代码——那会产生噪声 diff 与回归风险。

## 流程

1. **先理解再动手（Chesterton's Fence）**：改/删前先理解它为何存在。回答：它的职责？谁调用它/它调用谁？边界与错误路径？为何这样写（性能/平台约束/历史原因）？
2. **识别机会**：深嵌套(3+层)→抽 guard clause；长函数(50+行)→拆分；嵌套三元→if/else 或查表；布尔标志参数→选项对象；重复逻辑→抽共享函数；死代码→删除（确认后）。
3. **增量改动**：一次一处简化，每改完跑测试。重构与功能/修复分开提交。
4. **验证结果**：简化版真的更易理解吗？diff 干净可审吗？引入了不一致吗？不成功就 revert。

## 红旗

- 简化后需改测试才能过（你大概改了行为）
- "简化"版比原版更长更难懂
- 为匹配个人偏好而重命名（非项目约定）
- 因"更干净"而移除错误处理
- 批量多处简化塞进一个大 commit
- 越界重构未改动的代码

## 验证

- [ ] 现有测试无需修改即通过
- [ ] 构建无新警告
- [ ] Lint/格式化通过
- [ ] 每处简化都是可审的增量改动
- [ ] 未移除或削弱错误处理
- [ ] 未留死代码（未用导入、不可达分支）
