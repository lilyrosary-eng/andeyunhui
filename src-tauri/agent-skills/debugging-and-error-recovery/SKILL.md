# 调试与错误恢复（Debugging & Error Recovery）

## 概述

五步分诊法：先稳定复现，再定位根因，然后最小修复，最后防回归。杜绝"猜测驱动开发"——每一步都基于证据。

## 何时使用

- 报错/崩溃/异常堆栈
- 行为与预期不符
- 测试失败且原因不明
- 性能突然退化
- 间歇性故障

## 五步流程

### 1. 稳定复现
- 找到最小可复现步骤。间歇性 bug 先消除随机性（固定种子、移除并发、补日志）。
- 复现不了就修不了。先把它变成"必现"。
- 记录确切的环境：版本、平台、数据、参数。

### 2. 收集证据
- 读完整错误信息与堆栈，不要只看第一行。
- 沿调用链回溯：错在哪一层？数据从哪来？
- 加临时日志或断点，观察实际值（不要假设值"应该"是什么）。
- 二分定位：注释掉一半代码看故障是否消失，缩小范围。

### 3. 定位根因
- 现象 ≠ 根因。"数组越界"是现象，"数据源漏了空值过滤"才是根因。
- 连问五个为什么，直到触及可独立修复的最底层。
- 警惕"修了现象没修根因"——同样的 bug 会换个地方再出现。

### 4. 最小修复
- 改最少必要的代码解决根因。不要顺手重构。
- 修复后该故障 100% 不再复现，且不引入新行为变化。
- 如果修复比 bug 本身更复杂，重新评估：是不是根因找错了？

### 5. 防回归
- 加一条针对该根因的测试（先红后绿）。测试名应描述被保护的行为，而非修复方式。
- 检查同类风险点：同样的模式是否出现在别处？
- 记录根因与修复，便于未来排查。

## 常见陷阱

| 陷阱 | 对策 |
|---|---|
| 只看第一行报错 | 读完整堆栈，找最深的应用代码帧 |
| 改代码直到"好像好了" | 先复现，改后确认必现路径不再触发 |
| 修现象（加 try/catch 吞错） | 找根因；吞错只是把 bug 推到更难查的地方 |
| 顺手重构 | 修复与重构分开提交，避免回归时无法定位 |
| 跳过防回归测试 | 没测试的修复只是"暂时不报错" |

## 验证

- [ ] 故障可在修复前稳定复现
- [ ] 修复后该路径 100% 不再触发
- [ ] 新增针对根因的回归测试（先红后绿）
- [ ] 未引入新警告或行为变化
- [ ] 同类风险点已排查
