# 源驱动开发（Source-Driven Development）

## 概述

流程：DETECT → FETCH → IMPLEMENT → CITE。绝不凭记忆写框架代码——查文档、引源。

## 何时使用

- 用户要符合当前最佳实践的代码
- 构建会被复制的样板/起始代码
- 明确要求"正确/已验证"实现
- 框架推荐方式重要（表单/路由/数据获取/状态/auth）

**何时不用**：正确性不依赖具体版本（重命名变量、修错别字）；跨版本一致的纯逻辑；用户明确要速度优先于验证。

## 流程

### 1. Detect（检测版本）
- 读依赖文件：package.json / composer.json / requirements.txt / go.mod / Cargo.toml / Gemfile
- 版本不明就问用户，绝不猜

### 2. Fetch（抓文档）
- 抓"特定文档页"而非首页
- 权威优先级：官方文档 > 官方博客/changelog > Web 标准（MDN/web.dev）> 浏览器兼容（caniuse）
- **不引用** SO / 博客 / AI 摘要 / 自身训练数据

### 3. Implement（按文档实现）
- 按文档 API 签名而非记忆；新方式优先；弃用模式不用
- 文档没覆盖就标 unverified
- 文档与现有代码冲突时显式呈现冲突让用户选

### 4. Cite（引用源）
- 每个框架特定模式带引用
- 代码注释与对话中给完整 URL（深链带 anchor 优先）
- 找不到文档就明确标 UNVERIFIED

## 红旗

- 不查文档就写框架代码
- 用"我相信/我认为"而非引用源
- 不知模式适用版本
- 引用 SO/博客而非官方
- 用训练数据里的弃用 API
- 未读依赖文件就实现
- 无源引用

## 验证

- [ ] 从依赖文件识别版本
- [ ] 抓取官方文档
- [ ] 所有源为官方而非博客/训练数据
- [ ] 代码遵循当前版本文档模式
- [ ] 非平凡决策带完整 URL 引用
- [ ] 未用弃用 API
- [ ] 文档与代码冲突已上呈用户
- [ ] 无法验证者已显式标记 UNVERIFIED
