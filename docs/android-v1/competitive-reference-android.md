## 0. 说明与可信度标注

本文档拆解同类「本地优先 / 跨设备工具」的移动端设计，聚焦四个问题：

1. 移动端导航如何组织
2. 设备配对流程如何设计（**这是我们的门槛所在**）
3. 局域网发现失败时如何反馈
4. 本地优先产品如何在移动端表达「你的数据在你自己手里」

**可信度标注**：
- 🟢 **已核实** — 本轮通过公开资料检索确认
- 🟡 **一般认知** — 基于对产品的通用了解，细节可能随版本变化
- ⚪ **推断** — 基于产品类型的合理推测，使用前请自行验证

## 2. 逐个拆解

### 2.1 LocalSend ⭐ 最高优先级参考

> 我们的传输后端是它的协议兼容实现。**这意味着安得云荟手机版可以直接和官方 LocalSend 互传**——既是卖点也是威胁（PRD Q8）。

#### 核心事实 🟢

| 项 | 事实 |
| --- | --- |
| 技术栈 | Flutter |
| **APK 体积** | **约 16.7 MB** |
| 导航 | **三 Tab：接收 / 发送 / 设置** |
| **Tab 位置** | 🔴 **手机在底部，桌面在左侧竖排——同一套 UI 的两种排布** |
| 协议 | 自定义 LocalSend Protocol + HTTPS（每设备运行时生成自签 TLS 证书） |
| 设备命名 | **自动生成随机别名**（"Fast Strawberry"、"Strong Papaya"），可改 |
| 配对 | **无显式配对**。同网段自动出现在列表，发送时接收端弹确认 |
| 发现失败兜底 | **手动输入 IP** + **收藏夹（Favourites）** |
| 快捷入口 | 🔴 **注册为 Android 系统分享目标**（iOS 上不支持） |
| 便利开关 | **Quick Save** — 自动接受传输请求（用户自选，带风险提示） |
| 高级设置 | 端口、组播地址、设备类型、加密开关均可改 |

#### 🔴 最重要的一条发现

> **LocalSend 桌面版把三个 Tab 放在左侧竖排，手机版把同样三个 Tab 放在底部。**

这正是我们设计规范 §3.4 定义的 **Tab ↔ Rail 转换**（决策 24）。一个日活百万级的成熟产品用同一个方案，说明这条路径是被验证过的，不是我们臆造的。

#### 可借鉴

| # | 借鉴点 | 落到我们哪里 |
| --- | --- | --- |
| L1 | **同一套 UI，Tab 位置随宽度切换** | 设计规范 §3.4 已采纳 |
| L2 | **系统分享目标是核心入口，不是附属功能** | PRD P0-14 —— 这是我们「去 Windows 味」最有效的一招（决策 21），LocalSend 的实践佐证了这个判断 |
| L3 | **手动填 IP 作为发现失败的逃生舱** | 设计规范 §4.3.1 已采纳。组播在企业网/访客网必然失败，没有兜底就是直接丢用户 |
| L4 | **收藏/常用设备** | 我们的「已配对设备」概念更强（因为我们主打「我自己那台电脑」），可视为收藏夹的强化版 |
| L5 | 随机友好别名降低命名负担 | 我们可用「用户名的电脑」作为默认设备名，但**必须允许改** |
| L6 | Quick Save 开关（自动接收） | 建议列 P1。对「只和自己的电脑传」的场景，自动接收体验提升明显。**必须默认关 + 明确风险提示** |

#### 🔴 要避开的坑（LocalSend 被批评的点）

| # | 缺陷 🟢 | 我们的应对 |
| --- | --- | --- |
| X1 | **收到文件时不发系统通知**，用户必须自己切回 App 才知道 | PRD P0-15 前台服务 + 通知栏。**接收必须有通知** |
| X2 | **两端 App 都必须开着**才能传，没有唤醒机制 | 同上。我们的前台服务让手机端可后台接收；PC 端桌面版常驻本就成立 |
| X3 | 收到的文件**不能在 App 内打开**，必须去文件管理器 | 接收完成的通知/卡片应提供「用其他应用打开」 |
| X4 | 默认随机别名让人分不清哪台是自己的 | 我们默认用「XXX 的电脑」并在配对向导里让用户确认 |

#### 定位差异（我们为什么不是 LocalSend 的复制品）

| | LocalSend | 安得云荟 |
| --- | --- | --- |
| 使用场景 | **面对面临时传文件**（AirDrop 替代品） | **我和我自己的电脑的长期关系** |
| 设备关系 | 匿名、临时、平等 | **有主从**：手机是终端，PC 是本体 |
| 核心资产 | 无 | **PC 上的算力与文件** |
| 传输之外 | 无 | **AI 对话是主模块** |

> 这个差异是我们的立足点：LocalSend 是**管道**，我们是**终端**。所以我们做「已配对设备」「设备在线状态常驻抽屉顶部」「连回 PC 跑 AI」——这些对 LocalSend 都没有意义。

### 2.2 KDE Connect

#### 核心特征 🟡

| 项 | 做法 |
| --- | --- |
| 定位 | 手机与桌面的**深度联动**（通知同步、剪贴板、远程输入、文件传输、媒体控制） |
| 导航 | 设备列表为首屏 → 点进单台设备 → **该设备的功能插件网格** |
| 配对 | **显式配对**：一端发起请求，另一端接受，配对关系持久化 |
| 设备状态 | 明确区分「已配对在线 / 已配对离线 / 未配对可见 / 记住但不可达」 |
| 功能组织 | **插件化**，每台设备可单独开关插件 |

#### 🔴 最值得借鉴的一条：以「设备」为一级组织单元

KDE Connect 的首屏不是功能，是**设备**。功能是设备的下属。

这个心智模型和我们高度契合——我们整个产品都建立在「有没有连上我的电脑」之上。

**落到我们的设计**：
- 设计规范 §3.2.2：抽屉顶部常驻**设备状态行**（设备名 + 在线圆点）
- 设计规范 §4.6：我的页首屏就是**当前设备卡片**
- 这两处已经采纳了「设备是一等公民」的思路

#### 可借鉴

| # | 借鉴点 |
| --- | --- |
| K1 | **显式配对 + 持久化关系**。我们同样需要——因为要长期连同一台 PC 跑 AI |
| K2 | **四种设备状态的清晰区分**（在线/离线/可见未配对/记住但不可达）。比二元的「在线/离线」信息量大得多 |
| K3 | 每台设备的能力是可枚举的（插件列表）。对应我们：这台 PC 有没有 Ollama？有几个模型？——配对完成后应展示 |

#### 要避开

| # | 坑 |
| --- | --- |
| KX1 | KDE Connect 的插件网格对新用户信息量过载。我们首发只有两个功能，不构成问题，但**「模块」Tab 后续填满后要警惕**变成图标沼泽 |
| KX2 | 它的配对失败提示较弱（常见「设备不可达」而无原因）。这正是我们 P0-10 要超越的地方 |

### 2.3 Syncthing（Android）—— 主要作为反面教材

#### 核心特征 🟡

| 项 | 做法 |
| --- | --- |
| 定位 | P2P 文件同步，本地优先的旗帜性产品 |
| 导航 | 侧滑抽屉 + 多个列表页（设备 / 文件夹 / 状态） |
| 配对 | **交换设备 ID**（长串 Base32 字符），可扫二维码 |
| 配置 | 大量技术概念直接外露：文件夹类型、版本控制策略、忽略模式、监听地址、中继 |
| 移动适配 | 🔴 **本质是把桌面 Web UI 的概念原样搬到手机** |

#### 🔴 这就是「生搬硬套」的教科书案例

Syncthing Android 的问题**和我们上一轮 APK 的问题是同一类**：

| Syncthing 的病症 | 我们上一轮的对应 |
| --- | --- |
| 桌面端的配置概念全量搬到手机 | 桌面端的模块全量搬到手机 |
| 用户要理解「设备 ID」「文件夹 ID」「introducer」才能用 | 用户要理解花名体系与模块划分才能找到功能 |
| 首次使用需要在两台设备间来回操作 | 首次使用无引导 |
| 失败时给的是技术层错误 | 同上 |

> **这是本文档里最重要的一条对照。** 我们做 Android v1 的整个动机，就是不要变成 Syncthing Android。

#### 可借鉴（少数亮点）

| # | 借鉴点 |
| --- | --- |
| S1 | **二维码配对**。长 ID 手输不现实，扫码是唯一可用方案。→ 我们列 P2-05；若后续要做「手动填 IP」以外的高级配对，优先做扫码 |
| S2 | 明确的同步状态指示（同步中/最新/离线/出错） |
| S3 | 电量与网络条件的约束设置（仅 Wi-Fi、仅充电时）——**这一点我们应该学**：大文件传输时是否限制仅 Wi-Fi |

#### 要避开

| # | 坑 |
| --- | --- |
| SX1 | 🔴 **不要把技术概念外露给用户**。我们的 fingerprint、组播地址、端口，一律不进主流程，只放「高级设置」 |
| SX2 | 🔴 **不要要求用户理解架构才能用**。用户不需要知道什么是 UDP 组播，只需要知道「手机和电脑要连同一个 Wi-Fi」 |
| SX3 | 不要用长 ID 作为用户可见标识。我们的 fingerprint 只展示**后 6 位**用于校验（设计规范 §4.5） |

### 2.4 Tailscale

#### 核心特征 🟡

| 项 | 做法 |
| --- | --- |
| 定位 | 零配置组网（WireGuard 网络） |
| **Onboarding** | 🔴 **登录 → 完事**。复杂度全部藏在协议层 |
| 主界面 | **一个巨大的连接开关** + 设备列表 |
| 状态表达 | 极简：连上了 / 没连上，一眼可辨 |
| 设备列表 | 设备名 + 在线状态 + IP，点击可复制/操作 |

#### 🔴 最值得学的一条：把复杂度压进协议层，界面只留状态

Tailscale 底层是相当复杂的（NAT 穿透、DERP 中继、密钥轮换、ACL），但用户界面上**几乎什么都没有**。

对照我们：我们的复杂度是「组播发现 + 防火墙 + Ollama 绑定地址」。这些**不可能完全隐藏**（因为需要用户去 PC 上做操作），但可以：

| 原则 | 落地 |
| --- | --- |
| 能自动的绝不问用户 | 配对成功后**自动**写入 `http://<设备IP>:11434/v1`，绝不让用户手填 IP（设计规范 §4.5） |
| 必须用户做的，给逐条清单 | 配对向导 Step 2「PC 端要做什么」（PRD §5.1.1） |
| 状态用一个词说清 | 抽屉顶部设备行：「书房台式机 · 在线」 |

#### 可借鉴

| # | 借鉴点 |
| --- | --- |
| T1 | **主界面用一个显著的连接状态**统领全局 → 我们的「算力来源条」承担了类似角色 |
| T2 | 设备列表极简：名字 + 状态点 + 地址，不堆信息 → 设计规范 §4.3 已采纳 |
| T3 | onboarding 步数极少。**我们的配对向导 5 步已经偏多**，应审视能否压缩到 3 步（欢迎 → 权限+扫描 → 完成，把 PC 端清单做成扫描失败时才出现的分诊内容） |

> 📌 **这是一条对当前设计的挑战**：设计规范 §4.5 的 5 步向导，Step 2（PC 端清单）对**已经准备好的用户**是纯粹的阻碍。建议改为：默认直接扫描，扫到了就跳过清单；扫不到才展示清单。**列入待确认（见 §6）。**

### 2.5 Obsidian 移动版 ⭐ 处境最相似

> Obsidian 是本地优先的桌面笔记产品做移动端——**和我们的处境完全一致**。

#### 核心特征 🟡

| 项 | 做法 |
| --- | --- |
| 桌面端形态 | 多面板、侧边栏、命令面板、大量快捷键、插件生态 |
| **移动端策略** | 🔴 **不复制桌面布局，重建导航模型** |
| 移动端导航 | 左右两个抽屉（左=文件树，右=大纲/反链），中间是编辑区 |
| 手势 | 边缘滑动开抽屉；底部工具条承载高频操作 |
| 插件 | 生态保留，但**明确区分哪些插件支持移动端**（`isDesktopOnly` 标记） |
| 取舍 | 桌面独有能力（部分插件、复杂多面板）**直接不提供**，不做残缺版 |

#### 🔴 最值得学的一条：明确标记「桌面独有」，不做残缺移植

Obsidian 的插件清单里，桌面专属插件在移动端**直接不显示**，而不是显示了但点了报错。

对照我们：
- 桌宠、托盘、悬浮歌词、截图录屏在 Android 上**不加载**（PRD §2.1 已明确，设计规范 §10.2 已列出组件清单）
- 关键是**不要让它们以灰色/报错的形式出现在移动端界面上**——那比不做更糟

#### 可借鉴

| # | 借鉴点 |
| --- | --- |
| O1 | **移动端重建导航模型，而不是压缩桌面布局**。这是决策 10「先换导航壳」的正当性依据 |
| O2 | **桌面专属能力直接隐藏**，不做残缺版 |
| O3 | 双抽屉承载次级导航，中间保持内容专注 → 我们只用左抽屉（决策 15），单侧更简单，可以接受 |
| O4 | **底部工具条承载高频操作**。我们的 AI 对话页输入区、传输页主按钮已遵循此原则 |

#### 要避开

| # | 坑 |
| --- | --- |
| OX1 | Obsidian 移动版的抽屉手势与系统返回手势冲突长期被诟病。→ **这正是决策 16 要解决的问题**，我们的方案（避开左侧 24dp）是对的 |
| OX2 | 首次打开 Obsidian 移动版要先「选择 Vault 位置」，这一步劝退率高。→ 我们的对应是「配对 PC」，**必须提供跳过路径**（PRD US-13） |

### 2.6 自托管客户端：Immich / Jellyfin

#### 共同特征 🟡

| 项 | 做法 |
| --- | --- |
| 首屏 | **要求输入服务器地址**（URL / IP:端口） |
| 门槛 | 🔴 这是自托管类产品**最大的流失点** |
| Jellyfin 的缓解 | 局域网自动发现服务器，找到就列出来点一下 |
| Immich 的缓解 | 服务器地址 + 登录，有二维码/深链接方案 |
| 常见失败 | http/https 混淆、端口写错、反向代理路径错、证书自签被拒 |

#### 对我们的直接启示

**我们的「连回 PC」和「填服务器地址」是同一类门槛，但我们有优势**：

| | 自托管客户端 | 安得云荟 |
| --- | --- | --- |
| 地址来源 | 用户手输 | **组播自动发现** |
| 认证 | 账号密码 | **指纹双端确认，无账号** |
| 失败率 | 高 | 中（组播成功即零输入） |

> 因此我们**必须把「自动发现」做到极致**——这是相对自托管客户端的核心体验优势。手动填 IP 只能是逃生舱，绝不能变成主路径。

#### 可借鉴

| # | 借鉴点 |
| --- | --- |
| I1 | Jellyfin 的「自动发现 + 手动兜底」双路径 → 设计规范 §4.3.1 已采纳 |
| I2 | 连接失败时区分「地址不通」「服务未响应」「认证失败」三类 → 我们的分诊清单应同样分层 |
| I3 | 服务器版本兼容性提示 → **我们需要**：手机版与 PC 桌面版的协议版本不匹配时要有明确提示，而不是静默失败 |

### 2.7 Ollama 移动客户端（Enchanted / Ollama App 类）⭐ AI 部分最直接对标

> 这类 App 的定位就是「在手机上连回自己电脑上的 Ollama」——**与我们 AI 模块的定位完全重合**。

#### 核心特征 🟡 / ⚪

| 项 | 常见做法 |
| --- | --- |
| 配置 | 首屏要求填 **Ollama 服务器地址**（`http://192.168.x.x:11434`） |
| 🔴 最大痛点 | **用户不知道要在 PC 上设置 `OLLAMA_HOST=0.0.0.0`**。Ollama 默认只绑 `127.0.0.1`，手机必然连不上。这是这类 App 的头号差评来源 |
| 模型选择 | 拉取 `/api/tags` 列出可用模型，下拉框选择 |
| 界面 | **标准聊天窗口**：顶部模型下拉 + 消息气泡 + 输入框 |
| 状态表达 | 通常只有「连上/没连上」，且失败时提示笼统 |

#### 🔴 这里有我们最明确的差异化机会

**机会 1：把 `OLLAMA_HOST` 这个坑在向导里直接填平**

这是整个品类的共性痛点，而我们有别人没有的优势：**我们的 PC 端就是我们自己的桌面 App**。

| 别的客户端 | 安得云荟 |
| --- | --- |
| 只能在文档里写「请设置 OLLAMA_HOST」 | 配对向导 Step 2 直接列出（PRD §5.1.1 第 4 项） |
| 无法检测 PC 端状态 | 配对成功后**主动探测** `:11434/api/tags`，失败就精准指引（设计规范 §4.5 Step 5） |
| 用户要手输 PC 的 IP | **配对已经拿到 IP，自动写入**，用户零输入 |

> 📌 **这是安得云荟 AI 模块相对整个品类最硬的优势**：因为我们两端都做，可以把配置链路自动化。竞品做不到，因为它们没有 PC 端。

**机会 2：算力来源可见化**

这类 App 的界面都是标准聊天窗口，顶部一个模型下拉框。**「跑在我自己的电脑上」这件事在界面上完全不可见。**

我们的「算力来源条」（设计规范 §5.2、§6）正是针对这个空白：

| | 常规 Ollama 客户端 | 安得云荟 |
| --- | --- | --- |
| 顶部主控件 | 模型下拉框 | **算力去向条**（设备名 + 模型 + 出网与否） |
| 数据流向 | 界面上不体现 | 状态色 + 文案双通道表达 |
| 多后端 | 通常只支持 Ollama 一种 | **我的电脑 / 云端** 双后端 + 一键切换 |
| PC 掉线 | 报错 | **行内降级卡片 + 一键改用云端** |

**机会 3：PC 掉线的常态化处理**

家用 PC 会睡眠、会关机、会换网络。这类 App 普遍把它当异常处理（红色报错），而它其实是**常态**。

我们的行内降级卡片（设计规范 §4.1.1）针对的就是这个。

#### 要避开

| # | 坑 |
| --- | --- |
| EX1 | 不要做成「顶部一个模型下拉框」的第 500 个套壳聊天窗口 |
| EX2 | 不要让用户手输 IP |
| EX3 | 不要把「PC 不可达」做成红色报错 |
| EX4 | 不要在没有 PC 时把用户卡死（必须能退到云 API，PRD US-13） |

### 2.8 Home Assistant（移动端）

#### 核心特征 🟡

| 项 | 做法 |
| --- | --- |
| 发现 | 局域网自动发现 HA 实例，也支持手动填地址 |
| 内外网 | 区分「内部 URL」和「外部 URL」，按当前网络自动切换 |
| 失败反馈 | 相对详细，会区分网络不通 / 证书问题 / 认证失败 |
| 通知 | 深度使用系统通知与前台服务 |

#### 可借鉴

| # | 借鉴点 |
| --- | --- |

## 3. 横向对比

### 3.1 导航模型

| 产品 | 手机导航 | 宽屏导航 | 一级组织单元 |
| --- | --- | --- | --- |
| LocalSend 🟢 | **底部 3 Tab** | **左侧竖排 3 项** | 动作（收/发/设置） |
| KDE Connect 🟡 | 列表 → 详情 | — | **设备** |
| Syncthing 🟡 | 抽屉 + 列表 | — | 对象（设备/文件夹） |
| Tailscale 🟡 | 单页 + 设备列表 | — | 连接状态 |
| Obsidian 🟡 | 左右双抽屉 | 多面板 | 内容（笔记） |
| Immich 🟡 | 底部 Tab | — | 内容（照片） |
| **安得云荟（本案）** | **底部 4 Tab + 左抽屉** | **左 Rail + 双栏** | **能力（AI/内容/工具/我）** |

**结论**：
- 底部 Tab + 宽屏转 Rail 是被 LocalSend 直接验证过的路径 🟢，我们的决策 24 站得住
- 但我们的一级组织单元是「能力」，而 KDE Connect 用「设备」——考虑到我们同样高度依赖设备关系，**在抽屉顶部与我的页放置常驻设备状态**是必要的补偿（已在设计规范中采纳）

### 3.2 配对流程

| 产品 | 配对方式 | 用户输入量 | 兜底 |
| --- | --- | --- | --- |
| LocalSend 🟢 | **无显式配对**，同网即见 | 零 | 手动填 IP、收藏夹 |
| KDE Connect 🟡 | 显式配对请求 + 双端确认 | 零（点确认） | 手动填 IP |
| Syncthing 🟡 | 交换设备 ID | 🔴 高（长串 ID） | 二维码 |
| Tailscale 🟡 | 账号登录 | 低 | — |
| Immich/Jellyfin 🟡 | 填服务器地址 + 登录 | 🔴 高 | 自动发现（Jellyfin） |
| Ollama 客户端 🟡 | 填 IP:11434 | 🔴 高 | 无 |
| **安得云荟（本案）** | **组播发现 + 指纹双端确认** | **零** | **手动填 IP** |

**结论**：我们的配对方案在**用户输入量**这一维上处于最优档（与 LocalSend / KDE Connect 同级），显著优于自托管客户端与 Ollama 客户端。**这个优势必须守住——任何要求用户手输 IP 的设计都是倒退。**

### 3.3 发现失败时的反馈质量

| 产品 | 失败反馈 | 评价 |
| --- | --- | --- |
| LocalSend 🟢 | 列表空 + 可手动填 IP | 🟡 有兜底，但无原因说明 |
| KDE Connect 🟡 | 「设备不可达」 | 🔴 无原因 |
| Syncthing 🟡 | 技术层错误信息 | 🔴 普通用户读不懂 |
| Jellyfin 🟡 | 区分几类连接错误 | 🟢 较好 |
| Home Assistant 🟡 | 分层错误说明 | 🟢 较好 |
| **安得云荟（本案）** | **逐条可勾选的诊断清单 + 手动兜底** | 🟢 **目标：品类最优** |

> 📌 **这是我们可以做到品类第一的地方，而且成本很低——只是写清楚文案。**
>
> 整个品类在「扫不到设备」这件事上普遍摆烂（只显示一个空列表）。而这恰恰是用户最需要帮助的时刻。PRD P0-10 与设计规范 §4.3.1 的分诊清单，是一个低成本高回报的差异点。

### 3.4 「你的数据在你自己手里」的移动端表达手法

| 产品 | 表达手法 | 强度 |
| --- | --- | --- |
| LocalSend 🟢 | 官网/介绍文案强调「不用第三方服务器」；**界面内几乎不表达** | 🟡 弱（靠认知） |
| Syncthing 🟡 | 无中心服务器是架构事实，界面不特别强调 | 🟡 弱 |
| Tailscale 🟡 | 连接状态可见，但隐私靠品牌信任 | 🟡 中 |
| Obsidian 🟡 | 「文件就是你本地的 md 文件」——**用文件系统本身作为证据** | 🟢 强 |
| Immich 🟡 | 「你的服务器地址」常驻可见 | 🟢 中上 |
| **安得云荟（本案）** | **算力来源条常驻 + 每条回复溯源 + 出网显式标注** | 🟢 **强，且是实时的** |

#### 🔴 关键洞察

> **整个品类表达「本地优先」的方式，几乎都是静态的——靠架构事实、靠官网文案、靠用户的先验认知。**
>
> **没有一个产品做到「在使用的每一刻实时告诉你数据在哪」。**

Obsidian 做得最好，因为它有天然证据（你的笔记就是本地的 .md 文件，你能用文件管理器打开）。

而我们的场景更需要实时表达，原因是：**我们有多个后端**。同一个对话框，可能连着我家里的 PC，也可能连着 OpenAI。用户如果不知道当前是哪个，「本地优先」就是一句空话。

这就是设计规范 §6「算力可见的对话」方案的全部理由：

| 静态表达（品类现状） | 实时表达（我们） |
| --- | --- |
| 官网写「数据不出本地」 | 界面实时显示「未出网 / 数据出网」 |
| 隐私政策 | 每条回复带来源标记 |
| 用户需要相信 | 用户可以**看见**和**回溯审计** |
